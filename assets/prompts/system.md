# AI Games Collection MCP Server — System Guide

## Overview

AI Games Collection MCP is a FastMCP 3.2 server that provides AI-powered game analysis, correspondence play management, tournament organization, player rating tracking, and adaptive coaching across chess, Go, and Shogi. It integrates with professional AI engines — Stockfish 16 for chess (~3500 Elo), KataGo for Go (professional level), and YaneuraOu for Shogi (world champion level) — and supports P2P multiplayer synchronization via Firebase Realtime Database.

The server exposes 14 tools across 4 categories: Gameplay (game lifecycle), Analysis (engine evaluation), Management (tournaments and ELO), and Orchestration (SEP-1577 agentic workflows). All tools return structured JSON with a conversational message field for natural language rendering in MCP clients. The server supports both stdio transport for Claude Desktop and Cursor, and streamable HTTP transport for the React webapp dashboard.

## Architecture

The server is initialized in ai-games-collection-mcp/src/ai_games_collection_mcp/server.py where a FastMCP instance is created with a lifespan handler. The lifespan starts three core services sequentially: the database service (SQLite for game persistence), the engine service (manages connections to Stockfish, KataGo, YaneuraOu via aiohttp), and the sync service (Firebase Realtime Database for P2P multiplayer). Each service is a singleton that initializes connection pools during server startup and performs cleanup during shutdown.

Tool registration happens through four module files. gameplay.py handles new_game, make_move, get_game_state, and join_shared_session. analysis.py handles get_ai_move, analyze_position_detailed, and check_engine_health. management.py handles create_tournament, register_for_tournament, get_player_statistics, and update_player_rating. orchestration.py handles intelligent_game_analysis, adaptive_learning_session, and design_coaching_program using SEP-1577 sampling via ctx.sample() for agentic multi-step workflows.

The gateway server in web_sota/server.py wraps all of this with a FastAPI application that provides health check endpoints at /health returning service name and Tauri mode flag, REST status endpoints at /api/v1/status returning version and engine URLs, and CORS configuration for Tauri desktop app origins including tauri://localhost and all localhost variants. The FastMCP instance is lazy-mounted at /mcp during the server lifespan via asyncio.create_task, allowing the gateway to start serving HTTP immediately while the MCP server initializes in the background. This means the /mcp endpoint may not be available for the first 1-3 seconds after startup while the lifespan handler completes database initialization, engine connection setup, and Firebase sync initialization.

## Dual Transport Architecture

The server supports two transport modes selected at startup. In stdio mode, the server reads JSON-RPC requests from stdin and writes responses to stdout, which is the standard mode for Claude Desktop and Cursor integration. Stderr is used for all logging to prevent interference with the JSON-RPC protocol. In HTTP mode, the server starts a uvicorn ASGI server that serves the FastAPI gateway on the configured port with the FastMCP instance mounted at /mcp. This mode is used for the React webapp dashboard and for Tauri desktop integration where the backend runs as a child process.

## Game Engine Integration

The server integrates three professional game engines via HTTP bridge servers. Each engine runs as a separate process or Docker container and exposes a REST API for move evaluation and position analysis. The engine service in ai-games-collection-mcp/src/ai_games_collection_mcp/services/engine_service.py manages connection pools using aiohttp with configurable timeouts, retry logic, and health check intervals.

Stockfish 16 is the chess engine supporting UCI protocol commands via an HTTP wrapper. Running on port 11211 by default, it provides best move calculation at configurable depth from 1 to 30 ply, position evaluation in centipawns where positive values favor white and negative favor black, and multi-line analysis returning the top N variations at configurable depth. Stockfish can be compiled from source in the Docker build using the Dockerfile.stockfish which builds from the stockfish/ source directory, or it runs as a standalone binary. The engine is configured via the STOCKFISH_URL environment variable.

KataGo is the Go engine supporting GTP protocol commands with neural network-based evaluation running on port 11213. It provides move recommendations with winrate estimation expressed as a percentage, score prediction with territory counts for both players, and ownership heatmaps showing which player controls each intersection. KataGo requires a CUDA-capable GPU for optimal performance but can fall back to CPU evaluation with significantly reduced strength. The engine is configured via the GO_URL environment variable.

YaneuraOu is the Shogi engine supporting USI protocol commands with optional NNUE evaluation weights running on port 11212. It provides move evaluation for the Japanese chess variant with captured-piece drops, evaluation in centipawns, and principal variation display. YaneuraOu runs as a Windows binary in the yaneuraou/ directory with multiple executable variants optimized for different hardware configurations. The engine is configured via the SHOGI_URL environment variable.

All engine connections use HTTP POST requests with aiohttp for async I/O. The engine service manages connection pools with configurable timeouts defaulting to 10 seconds per request, automatic retry with exponential backoff up to 3 attempts starting at 500ms, and periodic health checks every 30 seconds that verify engine responsiveness. When an engine is unreachable, analysis tools return a clear error message identifying the affected engine by name and suggesting diagnostic steps.

## Services Layer

The database service in ai-games-collection-mcp/src/ai_games_collection_mcp/services/db_service.py wraps the SQLite database with aiosqlite for async operations. It provides methods for saving and loading games, managing tournaments, storing player ratings, and caching AI analysis results. All write operations use context manager-based transactions that automatically rollback on failure.

The engine service manages the HTTP connections to all three game engines. It maintains a dictionary of engine configurations including name, URL, and connection settings. The health check loop runs every 30 seconds, pinging each engine and updating the health status. The get_ai_move method sends the position to the appropriate engine and parses the response.

The game service handles game state transitions. It validates moves against the current position, updates internal state representations, and maintains the active games dictionary. Each game entry stores the game type, full move history, current position, status, and timestamps.

The sync service manages Firebase Realtime Database integration. On initialization, it loads the Firebase service account credentials from the FIREBASE_SERVICE_ACCOUNT_JSON environment variable and connects to the database URL specified in FIREBASE_DATABASE_URL. When a move is made in a shared game, it pushes the complete game state to /games/{game_id} as a JSON object. When get_game_state or join_shared_session is called, it reads the latest state from the same path.

## Database Schema

The SQLite database at data/ai_games_collection_mcp.db contains four tables. The games table stores game_id as TEXT PRIMARY KEY, game_type as TEXT, position as TEXT storing the current FEN or board representation, moves as TEXT storing a JSON array of all moves, status as TEXT with values active completed or aborted, created_at and updated_at as TEXT timestamps in ISO 8601 format, and metadata as TEXT storing a JSON object with optional fields. The tournaments table stores tournament_id as TEXT PRIMARY KEY, tournament_type as TEXT specifying the game type, status as TEXT, and metadata as TEXT storing a JSON object with player list, round information, and configuration. The player_ratings table contains player_id TEXT, game_type TEXT, rating INTEGER defaulting to 1500, games_played INTEGER, and last_updated TEXT, with a composite primary key on player_id and game_type. The ai_analysis_cache table stores position_hash TEXT as MD5 hash of position plus analysis parameters, game_type TEXT, best_move TEXT, evaluation TEXT, analysis_depth INTEGER, and expires_at TEXT, providing a cache for repeated analysis of the same position.

## Tool Categories

The Gameplay category handles the full lifecycle of correspondence games. new_game creates a game with a unique game_id that can be auto-generated as a random UUID or user-specified via the game_id parameter. The starting position for chess is the standard initial array with FEN rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1. For Go, the board starts empty at standard 19x19 size. For Shogi, the starting position follows standard Japanese rules with all 40 pieces placed according to tradition. make_move records a move with format varying by game type. For chess the move is in UCI format like e2e4 or g1f3. For Go the move is in SGF coordinate format like B[pd] for black at 4-4. For Shogi the move is in USI format like 7g7f or 8h2b+ for promoted moves. The tool validates the move, updates game state, syncs to Firebase, and persists to SQLite. Returns the full updated game state with the new position, all moves, and evaluation. get_game_state retrieves current state by game_id, syncing from Firebase first to catch remote moves then falling back to local cache. Returns complete game record. join_shared_session pulls a remote Firebase game into the local server by game_id, updating the in-memory game service with the remote position for continued analysis or play.

The Analysis category provides engine-powered evaluation with configurable parameters. get_ai_move sends a position to the appropriate engine based on game_type. The difficulty parameter adjusts engine strength: beginner reduces search depth and adds evaluation noise for approximately 1200 ELO play, intermediate uses standard settings for 1800 ELO play, and expert maximizes search for professional-level analysis. The depth parameter controls search depth in half-moves from 1 to 30. Returns best move in the appropriate notation format, evaluation score in centipawns for chess and Shogi or winrate percentage for Go, and principal variation showing the engine's expected continuation. analyze_position_detailed performs deeper multi-line analysis at configurable depth defaulting to 20. Returns multiple candidate moves each with evaluation and principal variation up to 8 half-moves deep. Includes tactical assessment flags for checkmate threats, forced captures, and hanging pieces. check_engine_health pings all configured engine URLs with HTTP GET and returns per-engine reaches boolean, response time in milliseconds, version string if available, and error details for unreachable engines.

The Management category handles tournament and ELO operations. create_tournament initializes a tournament with tournament_id, game_type, max_players, and optional time_control. time_control accepts blitz (1-5 minutes per game), rapid (10-20 minutes), standard (30-90 minutes), or correspondence (multi-day). Returns the tournament configuration with registration status. register_for_tournament adds a player by player_id, validating tournament existence, start status, and capacity. Returns updated participant count. get_player_statistics queries the database for a player's complete history across all or specified game types, computing current ELO, peak rating, games played, wins-losses-draws, win rate, average opponent strength, and recent trend. update_player_rating applies the standard ELO formula with configurable K-factor defaulting to 20. Takes player_id, game_type, opponent_rating, and result as win, loss, or draw. Returns new rating, rating change, expected score, and K-factor used.

The Orchestration category uses SEP-1577 sampling for autonomous multi-step workflows. intelligent_game_analysis chains multiple analysis tool calls at varying depths and synthesizes results into a structured report covering evaluation trend, critical moments, and strategic themes. The analysis_goal parameter focuses the evaluation: comprehensive_evaluation covers all aspects, tactical_opportunities searches for forced sequences, positional_assessment evaluates piece placement and structure, endgame_evaluation focuses on the final phase. adaptive_learning_session creates personalized training by loading player history, identifying weakness patterns in their play, designing targeted exercises, presenting interactive positions, and adapting difficulty based on performance. design_coaching_program generates a weekly curriculum with topics, materials, practice games, and checkpoints. The intensity parameter controls training frequency: light for 1-2 sessions per week, regular for 3-4 sessions, intense for daily sessions.

## Return Format

All tools return a consistent JSON structure. The success field is a boolean indicating whether the operation completed without errors. The message field contains a natural language summary string suitable for conversational rendering in chat interfaces. The data field is an optional dictionary containing structured results for follow-up tool calls including engine evaluations, game states, statistics, and program outlines. The next_steps field is an optional list of suggested follow-up actions. Error responses return success set to false, an error string with a descriptive message explaining the failure cause, and an optional recovery_hint string suggesting how to resolve the issue such as starting the engine server or verifying the game_id.

## Configuration

Configuration is managed through environment variables with sensible defaults in ai-games-collection-mcp/src/ai_games_collection_mcp/config.py. STOCKFISH_URL defaults to http://localhost:8000 for the Stockfish engine bridge. SHOGI_URL defaults to http://localhost:8001 for the YaneuraOu bridge. GO_URL defaults to http://localhost:8002 for the KataGo bridge. AI_GAMES_COLLECTION_MCP_LOG_LEVEL defaults to INFO and accepts DEBUG for verbose logging, WARNING for production, or ERROR for silent operation. AI_GAMES_COLLECTION_BACKEND_PORT defaults to 10987 for the FastAPI gateway when running in HTTP mode. AI_GAMES_COLLECTION_TAURI is set to 1 when running under the Tauri desktop wrapper. FIREBASE_SERVICE_ACCOUNT_JSON contains the Firebase service account credentials as a raw JSON string for P2P multiplayer sync. FIREBASE_DATABASE_URL specifies the Firebase Realtime Database endpoint URL.

## Tauri Desktop Mode

When running under Tauri (AI_GAMES_COLLECTION_TAURI=1), the server is spawned by the Rust operator as a child process. The operator sets the port via AI_GAMES_COLLECTION_BACKEND_PORT, creates the process with CREATE_NO_WINDOW flag on Windows, monitors stdout for the Uvicorn running string, and emits a backend-status ready event to the webview. During shutdown, the operator kills the child process. The Tauri webview serves the React webapp from static files bundled in the NSIS installer. CSP headers allow connections to localhost on the backend port.

## Error Handling

The server implements layered error handling with graceful degradation. Tool-level try/except blocks catch exceptions from all service calls, log the error with the module-specific logger at ERROR level, and return a structured error response. Service-level initialization failures during the lifespan handler are caught and logged but do not prevent the server from starting, allowing degraded operation with unavailable services. Engine communication errors trigger automatic retry with 500ms exponential backoff up to 3 attempts. Database errors use transaction rollback via aiosqlite context managers. Firebase sync failures log a warning at WARNING level and the server continues in local-only mode without data loss.

## File Structure

The ai-games-collection-mcp package is self-contained in ai-games-collection-mcp/src/ai_games_collection_mcp/. server.py initializes the FastMCP instance with lifespan handler and exports the http_app() function for HTTP mode. config.py reads all environment variables with defaults. database.py implements SQLite CRUD operations. help_system.py provides tool documentation. sampling.py implements SEP-1577 sampling orchestration. The models/ directory contains schemas.py with Pydantic models. The services/ directory contains db_service.py, engine_service.py, game_service.py, sync_service.py, orchestration_service.py, and ai/ with heuristics.py and minimax.py. The tools/ directory contains gameplay.py, analysis.py, management.py, and orchestration.py.

## Docker Deployment

The docker-compose.yml in the repo root defines four services: games-gateway on port 10987, stockfish-engine on port 11211, shogi-engine on port 11212, and go-engine on port 11213. All share a games-net bridge network. The gateway container builds from the root Dockerfile using Python 3.11-slim, copies the web_sota and ai-games-collection-mcp source, and runs uvicorn with the FastAPI gateway. A curl-based health check at /health runs every 30 seconds. Engine containers provide HTTP endpoints for the gateway to proxy analysis requests.
